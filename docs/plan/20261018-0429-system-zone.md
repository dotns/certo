# 20261018-0429-system-zone Manage the base domain as a system zone instead of config records

- **status**: rejected
- **createdAt**: 2026-10-18 04:29
- **approvedAt**: (pending)
- **relatedTask**: 20261018-0429-system-zone

## Context

Two serving paths exist (`crates/certo-dns`):

- `ChallengeResponder` (`challenge.rs`) answers `general.domain` and everything under it:
  an SOA built from `nsname`/`nsadmin` with a date serial, the static `general.records`
  lines parsed at startup into an immutable `FxHashMap<LowerName, Vec<Record>>`, and the
  challenge TXT rows of the `txt` table read on every TXT query (TTL 1). Static records may
  name anything, also outside the base domain; `static_owners()` feeds
  `ZonePolicy.reserved`, which stops hosted zones from covering them. Changing a static
  record means editing the config and restarting.
- Hosted zones (`zones.rs`, `zone.rs`): rows in `zones`/`records`, owned by a user
  (`zones.user_id NOT NULL`, no foreign-key pragma), rebuilt and DNSSEC-signed on every
  change into the catalog. `check_new_zone` refuses zones at or under the base domain and
  zones covering reserved names; `records::validate` refuses record names inside the base
  domain (`Reserved`).
- `DnsHandler` sends a query to the catalog only when the challenge responder does not own
  the name.

The API (`crates/certo-api/src/zones.rs`) serves the same per-zone handlers under
`/api/zones` (owner, scope-checked) and `/admin/zones` (`X-Admin-Key`); `ZoneCtx` compares
`zone.user_id` with the caller. The dashboard has no admin mode; the admin API is used
from scripts (`docs/api.md`, `llms.txt`).

The challenge TXT path cannot move into a catalog zone: TXT values change on every
certificate issuance and acme-dns keeps only the two newest, while a catalog zone is
rebuilt and signed as a whole on each change.

## Proposal

### 1. Storage (`certo-db`, schema 4)

- `zones.user_id` becomes nullable; `NULL` marks the system zone. Migration 3 → 4
  recreates the table (`zones_old` → `zones`, copy, drop) in one transaction; the
  foreign-key pragma is off, so dependent tables keep their `zone_id`.
- `Zone.user_id: Option<i64>`; `Zone::is_system()`.
- `Db::ensure_system_zone(name, nsname, seed: Vec<NewRecord>) -> Result<(Zone, bool)>`:
  inserts the row with the apex NS and the seed when no system zone exists, returns
  whether it was created. A system zone of another name (config `domain` changed) is
  reported as an error at startup: the operator renames or deletes it explicitly.
- `check_overlap` treats `NULL` as "another owner" for every user.

### 2. Serving (`certo-dns`)

- `ChallengeResponder` loses `records` from its config; it keeps a swappable snapshot
  `Arc<RwLock<Arc<Static>>>` (`records` map plus SOA) and gains
  `replace_static(records: Vec<Record>)`. `answer`, `is_authoritative` and the SOA come
  from the snapshot; the TXT path is untouched. `static_owners()` is removed.
- `Zones` takes the `ChallengeResponder`. `publish(name)` on the system zone materializes
  the records (same `materialize`, SOA from `nsname`/`nsadmin` and the zone serial) and
  calls `replace_static` instead of building a catalog zone; `load_all` therefore serves it
  like every other zone. Record validation for the system zone skips the `Reserved` rule
  (names must be inside the base domain, as for any zone).
- `ZonePolicy.reserved` goes away; `check_new_zone` keeps the "not at or under the base
  domain" rule.
- Refused on the system zone with `NotAllowed`: delete, DNSSEC, AXFR allow list and TSIG
  keys (it is not in the catalog, so none of these could take effect).

### 3. Startup and config (`certo`, `certo-core`)

- `main.rs`: after `Zones::new`, `zones.ensure_system(&config.general)`: parses
  `general.records` with the existing static-record parser into `NewRecord`s, keeps the
  lines inside the base domain (others are logged as errors with the hint to create a
  hosted zone through the admin API), creates the system zone when missing, then
  `load_all`. When the zone already exists and `general.records` is non-empty, log once:
  "general.records was imported into the base zone; remove it from the config".
- `general.records` stays in `Config` as the seed; `config.toml` sample and
  `docs/configuration.md` describe it as first-start seed only. `nsname`/`nsadmin` stay
  (SOA of every zone).

### 4. API (`certo-api`)

- `ZoneCtx` on user routes: `zone.user_id != Some(user.id)` → 404 (hides the system
  zone). `GET /api/zones` keeps listing the caller's zones only.
- `ZoneView` exposes `system: bool`; `owner` is `null` for it. Admin list includes it.
- `DELETE /admin/zones/<base>`, DNSSEC, transfer and TSIG handlers surface the
  `NotAllowed` as `403 zone_not_allowed` (existing mapping).
- `docs/api.md` and `llms.txt` / `llms-api.txt` describe the system zone and the admin
  record routes for it.

### 5. Tests (RED first)

- `certo-db`: schema 4 upgrade from the v3 fixture (zones keep their rows; `user_id`
  nullable), `ensure_system_zone` idempotency and seed, overlap against the system zone.
- `certo-dns`: `replace_static` changes answers without rebuilding; system zone publish
  updates the responder (A record visible, SOA serial bumped); DNSSEC/AXFR/delete refused;
  records outside the base domain rejected for the system zone; existing challenge tests
  switch from config records to seeded records.
- `certo-api`: admin edits base-domain records and the DNS answer changes; user cannot
  see `/api/zones/<base>`; `GET /admin/zones` lists the system zone with `system: true`.
- e2e: new case editing an apex record of the base domain through `/admin/zones` and
  checking `dig`; `helpers.ts` keeps `records` in the test config (seed path covered).

### 6. Docs

`docs/architecture.md` (serving paths, system zone, schema 4), `docs/configuration.md`
(`general.records` as seed), `docs/api.md`, `docs/deployment.md` (editing the base
domain's records; moving records that were outside the base domain into hosted zones),
README feature list, `docs/changelog.md`.

## Risks

- Behaviour change: static records outside the base domain are no longer served from
  config. They are logged at startup; the operator recreates them as a hosted zone via
  `/admin/zones`. Documented in the changelog and deployment guide.
- Schema 4 is one-way (as every upgrade): older binaries refuse the database.
- The SOA serial of the base domain changes from a date-derived value to the zone serial
  (unix time at last change, as hosted zones); secondaries of the base domain, if any,
  see a jump, not a decrease.
- `ChallengeResponder` and `Zones` become mutually wired; `DnsHandler` still owns the
  dispatch, so no cycle in ownership (`Zones` holds a clone of the responder).
- No admin dashboard: the system zone is edited through the admin API. An admin mode in
  the dashboard is a separate task.

## Scope

`crates/certo-db/src/{schema,zones}.rs`, `crates/certo-core/src/types.rs`,
`crates/certo-dns/src/{challenge,handler,zones,records}.rs`, `crates/certo-api/src/{zones,admin}.rs`,
`crates/certo/src/main.rs`, tests in all crates and `tests/e2e`, `config.toml`,
`llms.txt`, `crates/certo-api/src/llms-api.txt`, five docs files.

## Alternatives

- Separate `base_records` table and routes: no schema change to `zones`, but a second
  record editor and API; rejected, the point is one management path.
- Make the base domain a real catalog zone and move challenge TXT into it: needs online
  signing and per-query record injection into hickory's authority; large, and DNSSEC for
  the base domain is not asked for.
- Keep `general.records` as a live source merged with the database: two sources of truth
  for one name set; rejected.
- Drop `general.records` immediately without a seed: breaks every existing deployment's
  apex records on upgrade; rejected.
