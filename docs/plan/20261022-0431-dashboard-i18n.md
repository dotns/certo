## Context

`web/` has 2.9k lines of TSX across 11 routes, 20 feature components and 8 shared
components, all with inline English copy; `shared/lib/http.ts` maps API error codes to
English sentences; page titles are set with `document.title`. The product is used by
Chinese-speaking operators (README has a Chinese edition) and the pma-web baseline names
the stack for multi-locale products: `react-i18next` + `i18next-http-backend` +
`i18next-browser-languagedetector`, locale files under `public/locales/{{lng}}/{{ns}}.json`,
initialised in `app/i18n.ts`, mounted with `I18nextProvider`, detection
`localStorage -> navigator`.

## Proposal

1. **Stack** (latest stable, verified on npm 2026-10-22): `i18next` 26.5.4,
   `react-i18next` 17.1.0, `i18next-http-backend` 4.0.4,
   `i18next-browser-languagedetector` 8.2.1. `src/app/i18n.ts` configures one namespace
   `common`, `fallbackLng: 'en'`, `supportedLngs: ['en', 'zh-CN']`, detection order
   `localStorage` (key `certo-lang`) then `navigator`, `load: 'currentOnly'`. Locale
   files `public/locales/en/common.json` and `public/locales/zh-CN/common.json` are
   served by the embedded SPA like any asset. `Providers` mounts `I18nextProvider` and a
   `Suspense` boundary (the existing `Loading` component) while a locale loads;
   `<html lang>` follows the active language.
2. **Switcher**: a globe dropdown (English / 简体中文) in the app header next to the
   theme toggle and on the sign-in / sign-up pages.
3. **Copy**: every user-visible string moves to `t('<page>.<key>')` — navigation, page
   headers, cards, dialogs, form labels and descriptions, table headers, empty states,
   badges, toasts, confirm texts, document titles, the quick-start steps, protocol and
   client notes on the Clients page (snippet *code* stays as is), zone-file import
   "skipped" reasons. `errorMessage()` resolves API codes through `errors.<code>` keys
   (falls back to the code with underscores replaced, as today) and takes the `t`
   function so it works outside React too. Dates keep `toLocaleString()` with the active
   language.
4. **Chinese translation**: `zh-CN/common.json` written by hand, same key set; technical
   terms (zone, CNAME, TXT, DNSSEC, AXFR, TSIG, API key) stay in Latin letters as in
   `README_CN.md`.
5. **Tests**: `src/test/i18n.ts` initialises i18next synchronously with the English
   resources for Vitest (`react.useSuspense: false`); a new test asserts the two locale
   files have identical key sets and no empty values; `http.test.ts` and the zone-file
   tests pass a translator. Coverage threshold unchanged.
6. **Smoke**: the Playwright script runs its steps in English, switches to 简体中文, and
   takes screenshots of the main pages; the `lang` attribute and a translated heading
   are asserted.
7. **Docs**: README / README_CN dashboard bullets mention the two languages;
   `docs/README.md` concepts page notes the switcher; changelog; release `v0.3.0`.

Out of scope: translating API error `message` details produced by the server (they are
technical, e.g. PowerDNS rejections), localising the Rust side, more locales (the file
layout makes adding one a single JSON file plus a menu entry).

## Steps

1. Dependencies, `i18n.ts`, provider, switcher, test bootstrap, English locale file
   extracted from the current copy → web gates green with the English file only.
2. Replace inline strings page by page (auth, layout, overview, account, domains, keys,
   clients, zones, admin, shared components) → gates green after each group.
3. Chinese locale file + parity test → gates green.
4. Smoke run in both languages, docs, changelog, tag `v0.3.0`.

## Risks

- A key missing from `zh-CN` falls back to English (i18next fallback), never to a raw
  key; the parity test turns a missing key into a CI failure.
- Locale files load over HTTP on first paint: one small request, cached by the browser;
  the Suspense fallback shows the existing spinner.
- `errorMessage` signature changes (adds `t`); all call sites are in this repo.

## Alternatives

- Bundle the JSON into the app with static imports instead of `i18next-http-backend`:
  no extra request, but every locale ships to every user and departs from the baseline.
  Rejected while there are two locales; easy to switch later.
- LinguiJS (compile-time catalogs): smaller runtime, but another build step and
  tooling the baseline lists only as an alternative.
